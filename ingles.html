Inglês — Review P1

Simulado "4ºDSM – Review P1" respondido com o gabarito oficial. Vocabulário técnico de TI/DevOps (sprints, deploys, incidentes) com a resposta certa destacada e a explicação da regra gramatical usada em cada item.

Exercise 1 — Prepositions of time (at, in, on, from, to)

Item 1
Our daily stand-up meeting starts _____ 09:00 AM every morning.
Resposta: at — Usamos at para horários exatos no relógio (at 9:00 AM, at noon, at midnight).
Item 2
The DevOps team scheduled the server maintenance _____ Friday evening.
Resposta: on — Usamos on quando o período do dia (evening/morning/afternoon) vem acompanhado de um dia específico da semana (on Friday evening, on Monday morning).
Item 3
Sprint 4 begins _____ May 12th and ends _____ May 23rd.
Resposta: on / on — Usamos on para datas específicas (dias e meses): on May 12th, on Monday, on Christmas Day.
Item 4
We usually do major software deployments _____ the evening when user traffic is low.
Resposta: in — Usamos in para períodos do dia de forma genérica, sem um dia específico anexado (in the evening, in the morning, in the afternoon).
Item 5
The developers work on code reviews _____ 2:00 PM _____ 4:00 PM.
Resposta: from / to — A dupla from...to marca um intervalo de tempo com início e fim definidos (from 2:00 PM to 4:00 PM = "das 14h às 16h").

Exercise 2 — Modal verbs: can / can't (permission, prohibition, ability)

Item 1 · Permission
Developers _______ start work between 7:00 AM and 10:00 AM under the flexi-time policy.
Resposta: can — can expressa permissão ("é permitido"): a política de horário flexível permite começar nesse intervalo.
Item 2 · Prohibition
You _______ deploy untested code directly to production; it is strictly prohibited.
Resposta: can't — can't expressa proibição ("não é permitido"); a própria frase já confirma com "strictly prohibited".
Item 3 · Ability / Inability
Alex _______ fix backend bugs in Python, but he _______ write React components yet.
Resposta: can / can't — aqui can/can't indicam habilidade ou falta dela ("consegue" / "ainda não consegue"), não permissão. O contraste é marcado por "but ... yet".
Item 4 · Permission
We _______ take a break after 4 hours of continuous work in the software lab.
Resposta: can — novamente permissão: a regra do laboratório autoriza a pausa após 4 horas.
Item 5 · Prohibition
External visitors _______ enter the server room without an authorized security badge.
Resposta: can't — proibição: sem crachá de segurança autorizado, a entrada não é permitida.

Exercise 3 — Unscramble: polite requests with modal verbs (Can/Could)

Item 1
(you / check / the server logs / could / please / ?)
Resposta: Could you check the server logs, please? — Pedidos educados começam com o modal (Could/Can) antes do sujeito: Modal + subject + verb...? "Could" soa ainda mais formal/educado que "Can".
Item 2
(I / can / remote access / request / for the database / ?)
Resposta: Can I request remote access for the database? — Quando o próprio falante pede permissão para si mesmo ("posso...?"), a estrutura é Can/Could + I + verbo...?
Item 3
(we / reschedule / could / our progress meeting / to 3:00 PM / ?)
Resposta: Could we reschedule our progress meeting to 3:00 PM? — Pedido em grupo ("podemos...?"): Could + we + verbo...?
Item 4
(send / you / can / the updated API documentation / ?)
Resposta: Can you send the updated API documentation? — Pedido direto a outra pessoa: Can/Could + you + verbo...?
Item 5
(could / help / you / fix / this syntax error / me / ?)
Resposta: Could you help me fix this syntax error? — Estrutura com dois verbos: "help me + verbo no infinitivo sem 'to'" (help me fix, não "help me to fix" — ambas existem, mas sem "to" é mais comum no inglês falado/técnico).

Exercise 5 — Dialogue completion (Tech Lead & Developer)

Diálogo completo
Complete the dialogue between a Tech Lead and Developer using the phrases in the box: behind schedule | where are we | fix this | have a problem | on schedule

Tech Lead: Hi Alex! (1) Where are we with the payment gateway integration?

Developer: Well, we (2) have a problem with the database connection. The API keeps timing out.

Tech Lead: I see. Are we still (3) on schedule for Friday's release?

Developer: Unfortunately no. We are currently two days (4) behind schedule.

Tech Lead: How can we (5) fix this?

Developer: We can implement a temporary workaround and optimize the queries by tomorrow.

Por quê: "Where are we" pergunta o status atual de uma tarefa; "have a problem" introduz um obstáculo; "on schedule" = dentro do prazo, "behind schedule" = atrasado (opostos); "fix this" pede uma solução para o problema apresentado. Repare que o encaixe de cada frase depende do contexto da pergunta anterior — é assim que a prova cobra "reading comprehension" dentro do diálogo.

Exercise 6 — Technical vocabulary: choose A or B

Item 1
Users cannot log in because the authentication server suffered an unexpected…
  • A. outage
  • B. flexi-time
Por quê: "outage" = interrupção/queda de serviço, o termo certo para um servidor de autenticação parar de funcionar. "Flexi-time" é sobre horário de trabalho flexível, sem relação com falha técnica.
Item 2
The mobile app crashes on launch due to a memory leak…
  • A. bug
  • B. schedule
Por quê: um vazamento de memória que trava o app é um defeito de software, ou seja, um bug. "Schedule" (cronograma) não tem relação com o problema técnico descrito.
Item 3
Backend developers must resolve a critical… before proceeding with UI design.
  • A. deadline
  • B. blocker
Por quê: algo que precisa ser resolvido antes de continuar o trabalho é um impeditivo de progresso — exatamente a definição de blocker (visto no Exercise 4). "Deadline" é apenas o prazo final, não um impedimento em si.
Item 4
The team applied a temporary… while waiting for the official patch.
  • A. workaround
  • B. milestone
Por quê: uma solução temporária até a correção oficial chegar é um workaround. "Milestone" é um marco/etapa importante do projeto, sem relação com solução provisória.
Item 5
The build failed because the automated test suite detected a breaking…
  • A. syntax error
  • B. shift
Por quê: uma build que falha por causa dos testes automatizados geralmente é por um erro no código — um syntax error. "Shift" (turno de trabalho) não tem relação com falha de build.
